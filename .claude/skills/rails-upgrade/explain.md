# 理解の関門（既定値・雛形への追随の解説）

gems・rails-app-update・rails-defaults・rails-load-defaults から呼ぶ。Rails や gem の既定値・雛形の変化に追随するとき、担当者がレビュアーに説明できるようにする。

## 入口の条件

- 設定の「業務的な挙動の定義」に照らして、追随（業務的な挙動は変わらない）にあたる変化が見つかった。業務的な挙動が変わるなら、ここではなく [templates.md](templates.md) の「業務的な挙動の変化での停止」で止まる
- 変化の証拠がそろっている（応答のスナップショットの差分、[before-after.md](before-after.md) の設定の値の比較、生成されたファイルの差分）

## 手順

1. 項目に分ける。1 項目は、1 つの設定・1 つの雛形の変化
2. 項目ごとに一次の出典を確かめる（PR・CHANGELOG・gem のソース・ガイドの節。設定の「作業のルール」の出典の決まり）
3. [templates.md](templates.md) の「追随の解説」の型で、項目をまとめて示す
4. 返事を待つ。質問が来たら、同じ項目のまま答える。提案と違う扱い（採用しない、元に戻す）になったら、その理由も記録する
5. 記録の上乗せ（設定の「記録」）があれば、返事の内容を先に記録してコミットする（後のコミットのメッセージから指せるようにするため）
6. 変化をコミットする（[commit.md](commit.md)）。メッセージの本文に、解説の要点（何が・なぜ・影響）を書き、記録の上乗せがあればその ID を指す。スナップショットを作り直したら、変化を起こしたコミットに入れる

## 関門

- 理解の関門: 解説への返事

## 出口の条件と記録

- すべての項目に返事があり、コミットメッセージ（と記録の上乗せ）に残っている
- 雛形に合わせずに残した設定には、その場所に理由のコメントがある（[templates.md](templates.md) の「残す独自設定のコメント」）
