# 提示と記録の型

関門で示すもの、コミットと PR に書くものの型。人によっても回によっても、確かめる中身が同じになるようにするため、項目を省かない。当てはまらない項目は「なし」と書く。

人間がそのまま貼るもの（PR のタイトルと本文、PR やレビューへのコメント）は、表示した Markdown ではなく、コピーできるブロックで出す（下の「PR 本文」の「出し方」）。表示した Markdown をコピーすると、レンダリング後の文字になって貼れないため。AI が自分で使うもの（コミットメッセージ）は対象外

## 作業計画（判断の関門。research の出口）

```markdown
## <Step 名> の作業計画

### 目的と範囲
- 上げるもの: <gem・Ruby・Rails と版>
- 上げないもの: <と、その理由・時期>

### 調べたこと
| 項目 | 分かったこと | 出典 | テスト・E2E で守られているか |
|---|---|---|---|

### 決めたいこと
| 論点 | 案 | 根拠 | 見立て |
|---|---|---|---|

### 進め方
- 順番と、コミット・PR の単位
- 判断の関門の予定: ダウンロード（下の型で別に示す）、一時固定、手動確認の時期

### 確かめ方
- 完了条件（設定の「計画」の完了条件のうち、この Step に関わるもの）
```

## 質問（1 回に 1 論点）

```markdown
【論点 <N-1> のまとめ】<論点名>
<決めたこと。3〜5 行>

違っていれば指摘してください。指摘がなければ同意とみなします。

――――

【論点 <N>】<論点名>

<本題。根拠になるファイルと行、調べた事実と出典>

<決めたいこと、または食い違っている点>

<見立て>。論点 <N>（<論点名>）は、この見立てでよいですか。
```

- 答えを求める論点は、1 つのメッセージに 1 つだけ。前の論点のまとめは、答えを求めるものではなく、受け取り違いがないかの確かめ。最初の論点には、まとめの部分がない
- まとめの最後の文言（「違っていれば指摘してください。指摘がなければ同意とみなします。」）は省かない。時間が空いた後でも、黙っていると同意として扱われることが分かるようにするため
- 締めの文は、論点名を主語にする。「この案でよいですか」だけでは、何を指すか分かりにくいため
- 返事の扱い
  - まとめへの指摘があれば、次の論点に進まず、前の論点に戻って掘り下げる。直したまとめを、次の論点と一緒にもう一度示す
  - 返事に新しい前提や曖昧な点があれば、同じ論点のまま掘り下げる
  - まとめに触れずに次の論点に答える（掘り下げる）返事は、まとめへの同意とみなす
- 最後の論点は、作業計画の承認を兼ねる。質問の後に、決めたことを論点ごとに 1 行で並べ直し、「論点 <N>（<論点名>）は、この見立てでよいですか。よければ、決めたことがそろうので、この計画で進めます。」と締める。その返事を作業計画の承認とし、論点を決めた後に承認だけを別に聞かない

## ダウンロードの確認（判断の関門）

```markdown
| 名前 | 版 | サイズ | 入る理由（直接 / <gem> の依存） | 入れ先 |
|---|---|---|---|---|

- 公開日: <版ごと。公開から 2 週間たっているか>
- 照合: 落とした後に SHA-256 を rubygems.org などの値と比べる
```

- 依存で増えるものも含める。default gem と同じ名前の依存は、default gem の版で足りるか（落とさずに済むか）も書く

## 追随の解説（理解の関門。[explain.md](explain.md)）

項目ごとに 1 つ。

```markdown
### <項目>
- 種類: Rails の既定値 / Rails の雛形 / gem の既定値 / gem の雛形 ・ 対象: <アプリ>
- 何が変わるか: <前 → 後>
- なぜ起きたか: <変更の目的。出典の PR・CHANGELOG の要約>
- アプリへの影響: <確かめたこと。スナップショット・設定の値の比較の差分>
- 提案: 追随する / 採用しない（<理由>）
- 出典: <PR・CHANGELOG・gem のソース（gem名-版/ から）・ガイドのページと見出し>
```

- 返事をもらったら、この内容がコミットメッセージの本文になる（設定の「記録」に、記録の上乗せがあればそれにも）

## 業務的な挙動の変化での停止（判断の関門）

```markdown
### 止まった理由: 業務的な挙動の変化
- 変化: <前 → 後>（<スナップショット・テストの差分>）
- 起こした変更: <gem と版 / 設定 / 雛形>
- 出典: <PR・CHANGELOG>
- 設定で元に戻せるか: <戻せる（方法） / 戻せない>
- 選択肢: 元に戻す / 意図的な仕様変更として受け入れる / 上げるのをやめる
- 見立て: <どれがよいか、理由>
```

## コミットの報告（止まらない）

コミットしたら、続けて 1 回ずつ示す。

```markdown
- <コミット> <件名>（単位: <アプリ> / 理由: <1 行>。解説への返事: あり / 不要）
- 検査: <件数の要約>。スナップショットの差分: なし / あり（<理由。追随なら解説の項目>）
- lock: <動いた gem>。一時固定と default gem の版: 動いていない / 動いた（<理由>）
```

## PR 本文（pr の出口）

```markdown
## 概要
<何を、なぜ上げたか。版の表。計画と記録の場所>

## 変更の一覧
| コミット | 変わること | なぜ | アプリへの影響 | 出典・記録 |
|---|---|---|---|---|
| <理由 1 つにつき 1 行。同じ理由のアプリごとのコミットは、ハッシュを並べる> | | | | |
| <記録・計画だけのコミットは、最後の 1 行にまとめる> | 記録と計画 | | なし（文書だけ） | |

## 業務的な挙動の変化
なし（<確かめ方: スナップショット・E2E>）/ 意図的な仕様変更: <変化・理由・承認>

変わったが、業務的な挙動ではないもの（既定値・雛形への追随）:
- <項目>: <何が変わるか。業務的な挙動が変わらない理由>（<コミット・記録>）

## 確かめたこと
- <検査と件数、前後の比較、手動確認>

## 見送ったこと
- <採用しない雛形、後に回した gem と時期、改善の候補>

## レビュアーに見てほしい所
1. <優先順。業務的な挙動の変化、スナップショットの差分、判断の関門で決めたこと>
```

- 変更の一覧は、理由 1 つにつき 1 行にする。各行は、レビュアーが差分からコミットメッセージへたどれるように、コミットを指す（コミットを 1 行ずつ並べると、同じ内容の行と記録だけの行で長くなり、レビュアーが読みにくい）
- 追随は、業務的な挙動を変えないものとして、「業務的な挙動の変化」の節に並べる（レビュアーの物差しは業務的な挙動なので、変わったものが何で、なぜ業務的な挙動ではないかを、同じ節で見られるようにする）

### 出し方

本文をファイル（scratchpad）に書き、公開物の安全チェックを通してから、次の順に出す。

1. タイトル: ```` ```text ```` のブロック
2. 本文: 4 つのバッククォートの ```` ````markdown ```` のブロック（本文の中にコードブロックがあっても崩れないようにするため）
3. 本文のファイルのパス
4. `git push` と `gh pr create --base <向き先> --title "<タイトル>" --body-file <本文のファイル>` を、それぞれ `bash` のブロックで。タイトルをコマンドに入れるのは、PR の作り方によってはブランチ名がタイトルになるため

## 残す独自設定のコメント

雛形に合わせずに残す設定には、その場所にコメントを書く。次の `app:update` やジェネレーターの差分で、同じ判断をし直さないようにするため。

```ruby
# <なぜ雛形と違うのか>（<決めた記録への参照>）
<設定>
```
